# Workflow Изменений И Веток

Этот документ фиксирует практический workflow работы с репозиторием RodNIX.

## Базовая модель

- `main` — единственная постоянная ветка проекта.
- Все остальные ветки временные.
- Одна ветка должна соответствовать одной инженерной цели.
- После merge временная ветка удаляется локально и на `origin`.

## Именование веток

Разрешённые префиксы:

- `fix/<area>-<topic>`
- `feat/<area>-<topic>`
- `refactor/<area>-<topic>`
- `docs/<area>-<topic>`
- `build/<area>-<topic>`
- `test/<area>-<topic>`
- `ci/<area>-<topic>`

Примеры:

- `fix/net-e1000-rx`
- `feat/gfx-framebuffer-dev`
- `refactor/mm-layout-cleanup`
- `docs/arch-overview`
- `build/toolchain-macos`

Нельзя использовать:

- `dev`
- `tmp`
- `misc`
- `work`
- долгоживущие персональные ветки

## Рекомендуемый порядок работы

1. Обновить локальную `main`.
2. Создать короткоживущую ветку под задачу.
3. Выполнить изменение, обновить связанную документацию.
4. Прогнать минимальную валидацию.
5. Подготовить понятные коммиты.
6. Открыть PR или провести эквивалентный review-ready merge flow.
7. После merge удалить временную ветку локально и на сервере.

## Правила для `main`

- В `main` попадают только изменения, которые собираются.
- Если меняется поведение системы, активная документация обновляется в том же changeset.
- `main` должен оставаться пригодным для сборки и релизов.
- Теги релизов создаются только от `main`.

## Переписывание истории

Переписывание истории `main` допускается только как исключение и только
владельцем репозитория.

Допустимые причины:

- административная чистка истории;
- исправление неверных metadata;
- удаление секретов;
- исправление ошибочных tag / release refs;
- аналогичные одноразовые repository hygiene задачи.

Если переписывание истории всё же требуется:

1. использовать `--force-with-lease`;
2. заранее понимать, какие refs будут затронуты;
3. после push проверить `main`, теги и релизы.
