# Как XNU работает с процессором и потоком

Составлено 23 августа 2026 по `~/dev/xnu`. Повод — отладка зависания, в
которой моя правка закрыла гонку лишь наполовину (0/8 → 5/8), и стало ясно,
что упирается не в частность.

## Наша гонка, найденная измерением

Цикл ожидания:

```c
while (waitq_contains(q, self))   /* (A) поток ещё в очереди */
    scheduler_block();            /* (B) ставит BLOCKED */
```

Между (A) и (B) другой процессор снимает поток с очереди и будит его. Поток в
этот момент ещё `RUNNING`, будить нечего — и пробуждение пропадает. Поток
засыпает уже снятым с очереди, звать его больше некому.

Измерено: в зависшей системе поток `BLOCKED` с `waitq_owner == NULL`, остальные
ждут его, обе CPU простаивают, а сборщик крутится вхолостую.

## У XNU для этого окна есть имя

`osfmk/kern/thread.h:521`:

```c
#define TH_WAKING  0x100   /* between waitq remove and thread_go */
```

**Отдельное состояние ровно для промежутка между снятием с очереди и
пробуждением.** Окно не «не встречается» и не «закрыто аккуратностью» — оно
названо.

## Три вещи, которых у нас нет

### 1. Состояние — набор битов, а не перечисление

```c
#define TH_WAIT   0x01   /* queued for waiting */
#define TH_SUSP   0x02
#define TH_RUN    0x04   /* running or on runq */
#define TH_UNINT  0x08
#define TH_IDLE   0x80
#define TH_WAKING 0x100
```

Поток может быть `TH_WAIT | TH_RUN` одновременно — и именно это выражает наше
проблемное состояние: «уже помечен ожидающим, но ещё исполняется».

Смотри, что из этого следует в `thread_unblock()`:

```c
old_thread_state = thread->state;
thread->state = (old | TH_RUN) & ~(TH_WAIT | TH_UNINT | TH_WAIT_REPORT | TH_WAKING);

if ((old_thread_state & TH_RUN) == 0) {
    ready_for_runq = TRUE;
}
```

Пробуждение потока, который **всё ещё исполняется**, снимает с него ожидание и
**не кладёт его в очередь готовности**. Ровно правильная обработка моей гонки —
и она получается даром из представления.

С перечислением так нельзя: у поля одно значение, и любое присвоение теряет
половину истины. Наш `state` — перечисление. Это не деталь, а причина.

### 2. Замок на поток

`osfmk/kern/thread.h:453`, `1180`:

```c
decl_simple_lock_data(, sched_lock);      /* thread_lock() */
#define thread_lock(th)  simple_lock(&(th)->sched_lock, &thread_lck_grp)
```

Все переходы состояния планировщика идут под ним. `thread_go()` начинается с

```c
thread_lock_assert(thread, LCK_ASSERT_OWNED);
assert(thread->state & TH_WAIT);
assert(ml_get_interrupts_enabled() == false);
```

то есть будящий обязан держать замок потока и обязан застать его уже
помеченным ожидающим.

**У нас замка на поток нет вообще.** `scheduler_wake()` и `scheduler_block()`
меняют `state` без всякой взаимной защиты, с разных процессоров.

### 3. Пометка ожидания — под замком очереди, до переключения

`waitq_assert_wait64_locked()` вызывает `thread_mark_wait_locked()`, который
ставит `TH_WAIT`, **пока очередь заперта**. Переключение (`thread_block()`)
происходит позже и отдельно.

Порядок такой:

```
waitq_lock(q)
assert_wait(...)      → TH_WAIT выставлен, поток в очереди
waitq_unlock(q)
thread_block()        → только теперь переключение
```

Будящий, взяв тот же замок очереди, застаёт поток либо уже помеченным, либо ещё
не поставленным. Окна нет.

У нас пометка (`scheduler_block`) происходит **после** снятия замка очереди —
и окно есть.

## Устройство процессора

`osfmk/kern/processor.h`. `struct processor` содержит, среди прочего:

```c
struct thread     *active_thread;
struct thread     *idle_thread;
struct run_queue   runq;            /* очередь готовности этого процессора */
uint64_t           quantum_end;
uint64_t           deadline;        /* для ближайшего realtime-потока */
processor_set_t    processor_set;   /* кластер */
```

Существенное для нас:

- **очередь готовности на процессор**, а не одна на машину, как у нас;
- **`deadline` для ближайшего потока реального времени** — прямо в структуре
  процессора, то есть реальное время учитывается на уровне выбора процессора,
  а не поверх;
- **`processor_set`** — кластер процессоров с общей нагрузкой; на AMP-машинах
  это P- и E-ядра.

Данные на процессор объявляются `PERCPU_DECL` / `PERCPU_DATA` и размещаются
компоновщиком, а не массивом с индексацией по номеру CPU. У нас массив.

## Что из этого следует делать

Порядок — от причины к следствию, а не от простоты.

1. **Состояние потока — в биты.** `TH_RUN | TH_WAIT | TH_IDLE | TH_WAKING`.
   Без этого пробуждение исполняющегося потока невыразимо, и всякая заплата
   поверх перечисления будет закрывать одно окно из нескольких — что и
   произошло: 0/8 стало 5/8, а не 8/8.

2. **Замок на поток.** Все переходы состояния — под ним. Порядок относительно
   существующих замков объявить и проверить WITNESS-ом.

3. **Пометка ожидания под замком очереди**, до переключения. Тогда цикл
   `while (waitq_contains(...)) scheduler_block();` перестаёт быть нужен: он
   существует только потому, что между проверкой и сном есть щель.

4. Очередь готовности на процессор — отдельная работа, ради масштабирования,
   а не ради этой ошибки.

Флаг `wake_pending`, который я поставил, — это `TH_WAKING` без замка и без
битового состояния. Он закрывает часть окна и потому дал улучшение, но
оставшиеся отказы — это остальные части. Заплату стоит держать до пункта 1, а
затем убрать вместе с причиной.
