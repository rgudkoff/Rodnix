# Планировщик (целевой дизайн)

## Кого обслуживает планировщик

RodNIX делается для креаторов — музыка, видео и смежный real-time
медиаконтент (см. `overview.md`). Планировщик — подсистема, где это решение
имеет самые прямые последствия.

Аудио-поток не просит «побольше CPU», он просит **гарантию, что получит CPU не
позже дедлайна**. При 48 kHz и буфере 64 сэмпла период — 1.33 мс; один
пропущенный дедлайн слышен как щелчок. Поэтому качество планировщика здесь
измеряется не средней пропускной способностью и не долей fairness, а **верхней
границей задержки от события до выполнения**.

## Цели

- Ограниченная сверху задержка wake→run для latency-critical потоков — главный
  критерий; средняя пропускная способность вторична.
- Низкая латентность интерактивных задач без starvation фоновых.
- Предсказуемость под нагрузкой и наблюдаемость через метрики.
- Эволюция от текущего MLQ к иерархической модели `bucket -> group -> thread`.

## Источник архитектурного подхода

При проектировании используем идеи из внутреннего design-note по
иерархическому планированию `bucket -> group -> thread`.

Это не копирование реализации, а перенос принципов:
- приоритизация по QoS bucket,
- fairness между группами потоков,
- интерактивные окна (warp/starvation avoidance),
- отдельная политика для top-level выбора и thread-level time sharing.

## Текущий статус RodNIX (v1)

- **4 QoS-бакета**: `BACKGROUND(0) → UTILITY(1) → DEFAULT(2) → INTERACTIVE(3)`.
  Каждый бакет — отдельная FIFO-очередь; выше бакет = выше приоритет выбора.
- **Per-bucket квант**: INTERACTIVE × 1 тик, DEFAULT × 2, UTILITY × 4, BACKGROUND × 8
  (относительно базового `ticks_per_slice`).
- **Starvation avoidance**: если бакет не получал CPU 500 тиков — внеочередной слот.
- **`thread_group_t`** встроена в `task_t`: накапливает `cpu_ticks` и `last_run_tick`
  для всех потоков задачи (основа для честного распределения внутри бакета в v1.5).
- **`scheduler_set_bucket()`** — публичный API для явного назначения бакета потоку.
  Reaper-thread → BACKGROUND; все остальные потоки → DEFAULT по умолчанию.
- TIMESHARE/REALTIME + динамический приоритет для TIMESHARE.
- boost при пробуждении, penalty для CPU-bound, clamping.
- IPC priority inheritance: стек глубиной 8 (`inherit_stack[8]`),
  при переполнении `has_inherit_overflow` → безопасный откат к `base_priority`.
- deferred reaper + отдельный reaper-thread + базовые метрики reaper/stack-cache.
- единый `waitq`-путь ожидания для sleep/IPC с timeout-list.

## Разрыв относительно latency-цели

Текущий v1 даёт отзывчивость «в среднем», но не даёт границы сверху. Ниже —
проверенные по коду разрывы; они и есть содержание работ v2.

- **`SCHED_CLASS_REALTIME` влияет только на квант.** `scheduler_reset_timeslice()`
  выдаёт RT-потоку `REALTIME_QUANTUM_TICKS = 1`, но `ready_queue_index_for_thread()`
  не смотрит на `sched_class` вовсе (`sched/runqueue.c`). RT-поток стоит в том же
  бакете, что и обычный, и выбирается на общих основаниях. Класса реального
  времени как приоритетной сущности сейчас нет.
- **Нет дедлайнов.** Выбор — строго по номеру бакета, FIFO внутри. Пункт «1)
  Bucket level» целевой модели (EDF-подобный выбор с latency budget) не
  реализован.
- **Пробуждение не вытесняет.** `scheduler_wake()` только выставляет
  `resched_pending`; фактическое переключение делается на tick-векторах и по
  `VECTOR_RESCHED` (`kernel/arch/x86_64/isr_handlers.c`). IRQ устройства,
  разбудивший высокоприоритетный поток, возвращается в прерванный поток, а
  переключение ждёт следующего тика.
- **Гранулярность вытеснения — 1 мс.** LAPIC-таймер поднимается на 1000 Hz
  (`apic_timer_init(1000)` в `init/sysinit.c`), базовый слайс —
  `SCHEDULER_TIME_SLICE_MS = 10` (10 тиков). То есть worst-case задержка
  wake→run порядка тика сопоставима со всем аудио-периодом из примера выше.
- **TSC-deadline используется как периодический.** Режим поддержан и
  выбирается, но MSR программируется как `rdtsc64() + apic_timer_tsc_per_period`
  (`kernel/arch/x86_64/apic.c`) — то есть как фиксированный тик, а не как
  one-shot дедлайн под конкретный период клиента.
- **Память RT-пути может уйти в page fault.** Нет wired/`mlock`-памяти:
  в `kernel/posix/syscalls.master` нет `mlock`/`munlock`, в `mm/` нет
  wire-счётчика страниц. Гарантировать дедлайн на страницах, которые могут
  быть не резидентны, нельзя.
- **Переключение откладывается под спинлоком.** `scheduler_switch_from_irq()`
  при `percpu_preempt_blocked()` возвращает кадр как есть и переносит
  reschedule на следующий тик. Это корректно, но добавляет к верхней границе
  длину самой долгой секции под спинлоком — величину, которая сейчас нигде не
  измеряется.

## Целевая модель (v1-v2)

### 0) Real-time class

- Сделать `SCHED_CLASS_REALTIME` реальным классом, а не модификатором кванта:
  отдельная очередь выше всех QoS-бакетов, выбор до bucket-этапа.
- Поток RT-класса объявляет период и budget; планировщик проверяет допустимость
  при приёме, а не молча деградирует под нагрузкой.
- Вытеснение по пробуждению: wake RT-потока обязан приводить к переключению на
  выходе из того же IRQ, а не ждать тика.

Инвариант:
- принятый RT-поток получает CPU в пределах объявленного дедлайна либо приём
  явно отклоняется.

### 1) Bucket level (QoS)

- Ввести QoS bucket-и: `BACKGROUND`, `UTILITY`, `DEFAULT`, `INTERACTIVE`.
- Выбор bucket делать не только по статическому приоритету, а по дедлайну.
- Использовать EDF-подобный выбор bucket с latency budget (аналог WCEL).

Инвариант:
- high-QoS имеет lower latency target, но не может бесконечно вытеснять low-QoS.

### 2) Group level (Thread Group)

- Ввести `thread_group` (обычно process/service group).
- Планировать справедливость между группами в пределах bucket.
- Учитывать интерактивность группы: доля blocked/wakeup IPC vs CPU-bound.

Инвариант:
- один CPU-heavy процесс не должен выдавливать остальные группы того же bucket.

### 3) Thread level

- Внутри группы оставить decay/boost модель TIMESHARE.
- Поддержать inheritance donation/rollback для IPC-цепочек.
- Квант делать bucket-aware: интерактивные короче, фоновые длиннее.

## Окна для латентности и anti-starvation

### Warp window

- Короткое окно для резкого повышения интерактивной задачи после wakeup/IPC.
- Ограничение по времени и частоте, чтобы не разрушать fairness.

### Starvation avoidance window

- Если bucket/group долго не получает CPU, выделяется гарантированный слот.
- Метрика starvation фиксируется в статистике планировщика.

## Старт первого потока

Первый запуск инициируется через программный `int $32` в `scheduler_start()`,
чтобы использовать тот же IRQ-путь, что и обычная преэмпция.

Порядок:
1. `scheduler_start()` выставляет `resched_pending = true`.
2. Выполняется `int $32`.
3. IRQ32 вызывает `scheduler_tick()` + `scheduler_switch_from_irq()`.
4. Возвращается `interrupt_frame_t*` выбранного runnable-потока.

## Пошаговое внедрение

1. `v1`:
- Зафиксировать структуру `thread_group` и bucket enum.
- Добавить метрики latency/fairness/starvation.
- Вынести выбор bucket в отдельный этап (до MLQ выбора потока).

2. `v1.5`:
- Включить warp window и starvation avoidance window.
- Добавить per-bucket quantum policy.

3. `v2` (закрытие latency-разрыва):
- Выделить RT-класс в отдельную очередь выше бакетов.
- Вытеснение на выходе из IRQ, а не только на тике.
- EDF-подобный bucket scheduling с budget/deadline.
- One-shot TSC-deadline под период клиента вместо фиксированного тика.
- Wired-память для RT-путей, чтобы дедлайн не зависел от page fault.
- Расширенное inheritance для IPC-цепочек.

## Инварианты

- Контекст-свитч сохраняет/восстанавливает полный набор регистров.
- Решение планировщика детерминировано по фиксированным входам.
- Любой bucket/group получает CPU в ограниченное время (bounded starvation).
- Задержка wake→run для latency-critical потока ограничена сверху и измерима;
  ухудшение этой границы — регрессия, даже если пропускная способность выросла.

## Наблюдаемость

Обязательные счётчики:
- `context_switches`, `preemptions`, `voluntary_yields`,
- per-bucket runtime и wait-time,
- starvation events и warp activations,
- задержка wake→run: распределение и максимум за окно (не только среднее) —
  это основная метрика качества для целевой аудитории,
- максимальная длительность секции с запрещённой преэмпцией,
- reaper queue stats, stack-cache stats.
- waitq stats: `sleep_waiters`, `timed_waiters`.
